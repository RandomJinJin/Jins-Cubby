### 关键决策：混合模式必须用 lighten，不能用 screen
- `screen` = `1−(1−cb)(1−cs)`，会把近白底整体抬亮：浅灰 `#f5f5f5` 实测 Δ=7.6~11.8，页面出现明显白色圆斑；抬亮量与叠加色亮度成正比，调色板峰值消不掉
- `lighten` = `max(cb, cs)`，配合**调色板所有通道封顶 242**（低于底色 245）→ 浅色底是**数学上的零变化**（实测 Δ=0），黑色处 Δ=185~193
- 结论：凡是要「只作用黑色、浅色零影响」的混合遮罩，用 `lighten` + 峰值封顶，不要用 `screen`

### 模块设计：静态样式表 + 实例级 CSS 变量
- 样式表 `STYLE_SHEET` 静态、全部实例共用一份；配置差异走 `--irid-*` CSS 变量，由每个实例以内联样式写在自己元素上
- 好处：多实例并存互不干扰（实测 2 个实例各自尺寸/圆角/z-index 独立，仅 1 份样式表）；卸载后换配置重挂载也不会串配置
- 踩过的坑：最初写成「每个实例注入一份按配置编译的 CSS」，卸载重挂载时旧 style 标签残留导致用旧配置 → 改为变量方案后彻底解决
- `clampColor()` 是零变化的实现关键：把调色板每通道压到 `maxChannel` 以下

### 实测（headless Chrome + CDP 像素级测量）
测量须用「同一光标位置下开关遮罩、两次截图紧邻」，否则骰子自转会污染结果。注入固定色块排除 hover 干扰。
- 黑 `#1a1a1a` → rgb(191,158,212) Δ=193
- 白 `#ffffff` → Δ=0；浅灰 `#f5f5f5` → Δ=0
- 骰子描边黑 → 粉紫/蓝/紫渐变；白色骰面保持纯白
- about 页（可滚动）同样正常

### 坑位
- `html` 必须有背景色，否则 body 背景传播到 canvas，canvas 背景不参与混合组，遮罩退化成实色圆斑
- `.stage` 的 `opacity < 1` 会创建 stacking context 使 canvas 脱离根混合组；当前 `.stage.is-ready` 后 opacity=1 无影响，但后续加 `transform`/`filter`/`will-change` 会失效
- 本机默认 Node 22.22.2 不满足 Astro 要求（≥22.23.4），须用 `/c/Program Files/nodejs` 下的 v24.14.1
- Astro dev server 有单实例保护，`npm run dev` 报「Another astro dev server is already running」时说明已有实例在跑（可直接用，它带热更新）

### 关键洞察：hover 让位不需要 3D 投影挖洞
遮罩唯一能生效的像素就是悬停面本身 —— 其他区域要么白色骰面（max(255,≤242)=255 不变）、要么浅灰底（max(245,≤242)=245 零变化），本就零贡献。
所以「hover 时整体退场」在视觉上**完全等价于**「在 hover 区域让位」，却省掉 3D 顶点投影与每帧 DOM/WebGL 同步。实测抑制态截图与 `display:none` 截图 **SHA 完全一致** → 对画面零贡献，不是「变淡」。

### 坑：事件常量必须独立成文件
最初把 `DIE_HOVER_EVENT` 放在 `scripts/dice.ts` 里，导致 about/friends 页 import 它时**连带加载整个 620KB 的 three.js chunk**。
抽出 `src/config/events.ts`（34B）后，about/friends 只加载 4.8KB 布局脚本 + 34B 常量。
**通则：任何只需要一个常量的跨模块引用，都不要 import 那个重依赖模块。**

### 实测
- about / friends 页 `.irid-veil` 数量 = 0；主页 = 1
- hover 前 opacity=1 → 悬停后 opacity=0、is-suppressed=true → 移开恢复 opacity=1
- 视觉：悬停面纯黑、白数字清晰、零彩色圆斑；黑色色块上液态金属炫彩正常

### 待办
第 2 步「hover 面变液态金属」（GLSL 注入）未实施。第 1 步的抑制机制已顺带解决了原先担心的「DOM 遮罩与 three.js 二次叠加」问题（hover 时遮罩本就 opacity:0）。剩下要处理的只有数字可读性：金属底明暗变化会让深色数字在亮处糊，需设计「金属 + 深色数字 + 深色描边」。

- `src/styles/global.css` —— `.canvas-host` 新增 `isolation: isolate` + `background: var(--bg)`

### 关键洞察：作用域靠「隔离混合组」控制，不是靠 z-index 或裁剪
`mix-blend-mode` **只在最近的隔离组（isolated group）内混合**。遮罩挂在 body 下时 backdrop 是整个视口 → 页面上所有深色元素（黑色按钮、页脚文字、tooltip）全被染色。
解法：遮罩移进 `.canvas-host`，并给容器 `isolation: isolate` + **不透明背景** → 混合组内只剩画布像素，组外元素从原理上不可能受影响。
展开的骰子地图用同一块画布，自动保留炫彩。
**背景必须不透明**：透明区域 backdrop 为空时，遮罩会退化成盖在页面上的实色圆斑。

### 通则：挂载点应与「效果作用域」所在处一致
遮罩的作用域 = 骰子画布 → 就该由画布宿主组件（DiceStage）挂载，而不是全局布局（BaseLayout）。
副产品：about/friends 页连遮罩代码都不加载了（产物里只剩一个 625KB 的 DiceStage chunk，含 three.js + 遮罩）。

### 测量方法的重要教训
**只比截图哈希会得出错误结论。** 骰子自转会造成抗锯齿抖动，产生大量灰阶差异像素（本例 556 个），看起来像「远处描边被染色」，实际饱和度差 = 0，是纯抖动。
必须再区分「彩色差异」（染色，R/G/B 通道变化不一致，sat>20）与「灰阶差异」（抖动）。
判定标准：**彩色像素数 = 0** 才算真正无影响。已据此写了最小 PNG 解码器做像素级分析。
